# Signing Accessibility Remediation Report

This report covers the recipient signing experience for the current V2 envelope flow and the legacy V1 document flow. The audit focused on WCAG 2.2 A and AA criteria that affect signing a document, adding a signature, navigating the signing panel, and activating fields.

## Summary

| Area | Status | WCAG 2.2 criteria |
| --- | --- | --- |
| Signature pad dialog name and instructions | Remediated | 1.3.1, 3.3.2, 4.1.2 |
| Signature tabs role relationships | Remediated | 1.3.1, 2.1.1, 4.1.2 |
| Typed, drawn, and uploaded signature controls | Remediated | 1.1.1, 2.1.1, 3.3.2, 4.1.2 |
| V2 canvas field keyboard activation | Remediated for field activation | 2.1.1, 2.1.3, 2.4.7, 4.1.2 |
| Signing panel headings and progress | Remediated | 1.3.1, 2.4.6, 4.1.2 |
| V1 field removal and mobile panel buttons | Remediated | 2.5.3, 4.1.2 |

## Findings and remediation

### Signature dialog lacked a programmatic name

The shared signature dialog opened without a `DialogTitle` or description, which made the dialog context unclear for assistive technology. The dialog now has a title, description, and a named trigger that announces whether the signer is adding or changing a signature.

### Signature tabs used invalid ARIA

The custom signature tab list used an invalid `tabslist` role and did not connect tabs to their panels. The tab component now uses `tablist`, `tab`, and `tabpanel` with stable `aria-controls` and `aria-labelledby` relationships.

### Signature inputs were not consistently named

The typed signature input relied on placeholder text, canvas previews did not expose fallback text, and upload/color controls were missing accessible names. The controls now include programmatic labels and canvas fallback content.

### V2 signing fields were pointer-only

V2 fields are visually rendered on a Konva canvas. A keyboard-focusable DOM activation layer now sits over signer fields and calls the same signing logic as pointer activation. This gives keyboard and screen-reader users named controls such as **Insert Signature field**.

### Signing progress was visual only

The desktop sidebar and mobile signing widget progress bars now expose `role="progressbar"` with `aria-valuemin`, `aria-valuemax`, and `aria-valuenow`.

### Icon-only and empty controls were unnamed

V1 field insertion/removal buttons and mobile expand/collapse controls now use button semantics and accessible names. The V1 signing panel heading level was also adjusted to avoid skipping from the document title to a lower heading level.

## Automated coverage

The Playwright accessibility suite includes `packages/app-tests/e2e/accessibility/signing-accessibility.spec.ts`.

The test seeds a real pending envelope, opens `/sign/:token`, and verifies:

1. The signing page exposes expected headings and progressbar state.
2. Axe scans the signing sidebar for WCAG 2.0 A, WCAG 2.0 AA, and WCAG 2.2 AA serious or critical violations.
3. Axe scans the signature dialog after it opens.
4. The typed signature input is reachable by label.
5. The V2 signature field can be focused and inserted with the keyboard.
6. Progress updates to 100% after keyboard field activation.

## Remaining limitations

The accessibility test focuses on serious and critical WCAG violations in the remediated signing controls. Full PDF document content accessibility still depends on the accessibility of the uploaded PDF itself. Checkbox and radio field keyboard targets are exposed when option metadata is available, but complex option layouts should receive additional manual assistive technology testing before being considered fully certified.
